# 🖥 Автономный сервер для трейдинга и крафтов (архитектурный план)

Сейчас «ШКОЛА ДРОП» — полностью клиентская игра: весь прогресс живёт в `localStorage`/cookie игрока,
серверной части нет, сайт раздаётся как статика (Vercel). Это отлично для симулятора, но
**трейдинг (обмен между игроками) и крафты требуют общего сервера** — только так можно гарантировать,
что предмет реально перешёл из одного инвентаря в другой и что рецепт крафта никто не подделал.

Ниже — рабочий план, как добавить такой сервер, минимально трогая текущий фронтенд.

---

## 1. Что должен делать сервер

| Функция | Зачем сервер |
|---|---|
| Аккаунты и синхронизация сейва | чтобы инвентарь нельзя было «нарисовать» в localStorage |
| Трейдинг | комнаты обмена: оффер → контр-оффер → двойное подтверждение → атомарная передача предметов |
| Крафты | рецепты (например, 5 школьных предметов → 1 случайный редкий), сервер сам списывает ингредиенты и выдаёт результат |
| Античит | итоги крафтов/трейдов считаются только на сервере (`crypto.randomInt`), клиент лишь показывает результат |
| Лента сделок / история | публичная история трейдов, защита от скама |

## 2. Вариант А (быстрый): serverless на Vercel

Раз игра уже на Vercel, можно не поднимать отдельный хост:

```
api/
├─ account.js      # вход по нику (профиль уже есть) → выдача session-токена
├─ inventory.js    # GET/PUT синхронизация инвентаря
├─ trade/
│  ├─ create.js    # создать предложение обмена
│  ├─ accept.js    # принять / обновить оффер
│  └─ confirm.js   # финальное подтверждение обеих сторон
└─ craft.js        # POST { recipeId } → списать ингредиенты, выдать результат
```

* Хранилище — **Vercel KV / Upstash Redis** (быстро и бесплатно на старте) или Postgres (Supabase/Neon).
* Минус: serverless плохо держит живые WebSocket-комнаты — трейдинг будет по поллингу (опрос раз в 2–3 сек).

## 3. Вариант Б (полноценный): автономный сервер Node.js

Для живого трейдинга в реальном времени — отдельный процесс на VPS/Render/Railway/Fly.io:

```
server/
├─ index.ts        # Fastify/Express + WebSocket (socket.io или ws)
├─ auth.ts         # токены сессий (JWT или opaque), вход по нику + ПИН
├─ db.ts           # SQLite для старта → PostgreSQL при росте
├─ trades.ts       # комнаты обмена, состояния: draft → locked → confirmed → done/cancelled
├─ crafts.ts       # рецепты из общего конфига, серверная валидация
└─ antirug.ts      # rate-limit, проверки «предмет ещё существует и не выставлен дважды»
```

**Ключевые принципы:**

1. **Предметы живут только на сервере.** У каждого предмета — серверный `uid` (он уже есть в сейвах игры!).
   Трейд/крафт — транзакция над этими uid. Клиентский localStorage остаётся кэшем для оффлайна.
2. **Трейд — транзакция.** `BEGIN; проверить владельцев; переписать owner; COMMIT`. Либо всё, либо ничего —
   так предметы не дублируются и не исчезают.
3. **Двойное подтверждение.** Обе стороны сначала «замораживают» оффер (предметы залочены), потом нажимают
   «Подтвердить» — и только тогда сервер передаёт предметы.
4. **Крафт считается на сервере.** Клиент шлёт: `{ recipeId, ingredientUids[] }`. Сервер проверяет рецепт
   (минимальная суммарная цена / конкретные предметы), генерирует результат через `crypto.randomInt`
   (тот же принцип честного RNG, что и в кейсах), списывает ингредиенты.
5. **Бета-гейты:** фичи открываются только аккаунтам с флагом `betaTester` — тот самый закрытый бета-тест,
   который уже есть в игре (флаг надо будет синхронизировать на сервер).

**Пример рецепта крафта (для `js/config.js` в будущем):**

```js
const CRAFT_RECIPES = [
  { id: 'snack_upgrade',  name: 'Обед богов буфета', out: 'random_rare',
    rule: { count: 5, minTotalPrice: 1000, rarity: { in: ['consumer','industrial'] } } },
  { id: 'cat_summon',     name: 'Призвать кота',     out: 'cat_murka',
    rule: { items: ['cat_whiskers', 'cat_tail', 'sch_milk'] } },
];
```

**Минимальный план запуска:**

```bash
mkdir server && cd server
npm init -y && npm i fastify @fastify/websocket @fastify/cors better-sqlite3
node index.js        # слушает 0.0.0.0:3001
# задеплоить на Render/Railway → получить https://api.shkoladrop.example
```

Фронтенд при этом добавляет один модуль `js/net.js` с базовым URL API и обёрткой `fetch`/`WebSocket`.
Для прод-деплоя на Vercel URL сервера кладут в переменную окружения/конфиг, а не хардкодят.

## 4. Порядок внедрения (итеративно, ничего не ломая)

1. **Сервер-минимум:** БД + вход по нику (профиль в игре уже имеет ник — он станет логином).
2. **Синхронизация сейва:** кнопка «Привязать прогресс к аккаунту» — разовая заливка текущего сейва,
   дальше сервер становится источником правды для инвентаря.
3. **Крафты первыми:** они проще (не нужны вторые игроки и websocket) — хороший прогон всего пайплайна.
4. **Трейдинг:** комнаты по коду приглашения (как «комната по ссылке»), потом — таблица открытых предложений.
5. **Античит-проход:** перенос выдачи результатов крафтов/дропов с клиента на сервер там, где это важно.

## 5. Что НЕ делать

- ❌ Не доверять клиенту цены, редкости и результаты — клиент только отображает.
- ❌ Не хранить деньги/пароли игроков без хеширования; лучше обойтись ником + ПИН + токен.
- ❌ Не гонять весь сейв по сети на каждый клик — синхронизировать дельты (трейд, крафт, покупка).
